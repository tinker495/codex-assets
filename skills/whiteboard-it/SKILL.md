# Whiteboard it

사용자가 요청한 내용을 Whiteboard에 작성한다. 독자가 앞선 대화를 읽지 않아도 핵심을 이해하고, 근거를 확인하고, 필요한 판단을 내릴 수 있게 한다.

## 범위

- 주제와 깊이는 사용자의 요청에 맞춘다. 코드, 개념, 계획, 비교, 분석을 모두 다룬다. 기술 주제가 아니라는 이유로 코드 리뷰로 바꾸지 않는다.
- 실행이나 수정을 요청받았다면 그 작업과 검증도 수행한다. Whiteboard 설명만 작성하고 원래 작업을 완료했다고 보고하지 않는다.
- 같은 주제의 후속 요청은 기존 보드를 갱신한다. 별도 보드가 필요하거나 주제가 바뀌면 새로 만든다.

## Whiteboard 작성

1. 사용 가능한 Whiteboard 도구를 찾고 `session_capabilities`로 현재 기능을 확인한다. 기능 지원 여부를 이전 실행에서 가져오지 않는다.
2. 요청에 맞는 작성 지침을 읽고, 도구가 정한 순서대로 작성한다.
   - 저장소, 변경, PR 설명은 `session_get_instructions({topic:"authoring"})`를 읽는다. 사용자가 지정한 저장소와 비교 기준을 유지한다. 변경 리뷰에는 문서가 요구하는 파일 렌즈 작업과 위임 절차를 적용한다.
   - 저장소 없는 주제는 scratchpad 지원 여부를 확인하고 `session_get_instructions({topic:"scratchpad"})`를 읽는다. 반환된 지침이 해당 작업을 지원할 때 그 절차로 작성한다.
   - 기존 보드는 먼저 `session_get`으로 읽는다. 출처나 비교 기준이 바뀐 경우에만 대상을 갱신한다.

작성 중에는 다음을 지킨다.

- 현재 소스 설명과 변경 리뷰를 구분한다. 변경 리뷰는 실제 diff를 확인하고, 현재 동작 설명은 해당 소스를 확인한다. 설명을 만들려고 가짜 변경이나 무관한 저장소를 붙이지 않는다.
- 생성 결과가 이미 Desktop을 열었다면 다시 열지 않는다. 문서 쓰기는 `session_activity`로 lease를 확보하고, 같은 범위의 쓰기에 그 `leaseId`를 전달한다. 긴 조사 중에는 lease를 갱신한다.
- 짧은 설명부터 작성하고 필요한 도식을 붙인다. `session_edit`으로 작은 단위로 추가하며, 새 도식은 필요한 노드와 연결을 갖춰 한 번에 삽입한다. 후속 수정에는 반환된 컴포넌트 ID를 사용한다.
- 응답을 잃어 재시도할 때는 같은 `commandId`와 같은 입력을 재사용한다. 다른 작업은 새 UUID를 쓴다. 다른 세션의 lease와 충돌하면 덮어쓰지 않는다.

도구가 없거나 요청한 작성 방식이 비활성화돼 있으면, 무엇이 막혔는지와 필요한 설정을 짧게 알린다. 작성 가능한 내용은 채팅 초안으로 제공하되, Whiteboard에 저장하지 못했다는 사실을 밝힌다. 다른 제품을 Whiteboard 결과로 내놓거나 성공했다고 꾸미지 않는다. Whiteboard 내부 파일이나 SQL을 직접 수정하지 않는다.

## 읽는 순서

독자가 먼저 알아야 할 답을 앞에 둔다. 복잡한 내용은 전체 관계를 먼저 보여주고 세부 설명을 잇는다. 항목 수나 문서 길이를 미리 고정하지 않는다. 짧은 요청은 짧게 끝낸다.

- 관계나 분기를 이해해야 하면 `flow_diagram`, 시간에 따른 상호작용은 `sequence`를 우선 고려한다. 실제 데이터 구조가 핵심이면 도구가 지원하는 데이터 도식을 쓴다.
- 비교는 같은 기준으로 맞춘 표를 쓴다. 절차는 실행 순서를 보여준다. 차트가 필요하면 단위와 비교 기준을 적는다. 도식이 의미를 더하지 않으면 글만 쓴다.
- 도식의 노드와 연결에는 구체적인 대상을 적는다. 연결이 순서, 호출, 조건, 의존성 중 무엇을 뜻하는지 알 수 있게 한다. 색에만 의미를 맡기지 않는다.
- 낯선 용어는 처음 나올 때 짧게 설명한다. 이해를 돕는 구체적인 예시가 필요하면 하나를 들고, 가정한 예시와 관측한 사실을 구분한다.
- 코드 설명은 확인한 파일과 줄 범위를 연결한다. `review-source:` 링크와 소스 컴포넌트는 도구의 현재 형식을 따른다. 코드 식별자, 수치, 단위, 오류 메시지는 그대로 보존한다.
- 근거, 추론, 제안, 미확인 사항을 구분한다. 실제 동작과 변경 제안이 같은 도식에서 섞이면 상태를 명시한다. 요청하지 않은 선택지나 결정 배경을 지어내지 않는다.

## 기본 문체

[caveman](/Users/mrx-ksjung/.agents/skills/caveman/SKILL.md)의 `full` 압축 원칙과 [korean-humanizer](/Users/mrx-ksjung/.agents/skills/korean-humanizer/SKILL.md)의 자연스러운 한국어를 함께 적용한다. 세부 윤문 규칙이 필요하면 korean-humanizer의 `instruction.md`를 읽는다. 이 스킬에서는 사용자의 요청에 따라 Whiteboard 본문에도 아래 문체를 적용한다.

- 한국어를 기본으로 쓴다. 사용자가 다른 언어를 지정하면 따른다. 코드와 식별자는 원문을 유지한다.
- 답부터 쓰고, 한 문장에 한 가지 뜻을 담는다. 조사와 문법은 지킨다. 원인, 조건, 부정, 예외를 생략해 의미를 바꾸지 않는다.
- 인사말, 아첨, 반복 설명, 추상적인 수식어를 덜어낸다. 번역체, 불필요한 명사화와 피동은 자연스러운 동사로 고친다.
- 같은 대상은 같은 용어로 부른다. 생소한 축약어를 만들지 않는다. 토큰 수보다 읽고 이해하는 시간을 우선한다.
- 제목과 도식 라벨은 짧게 쓴다. 본문은 자연스러운 문장으로 잇는다. 이모지, 과도한 굵은 글씨, 장식용 줄표를 붙이지 않는다. 도식의 실제 연결선은 사용한다.
- 짧게 쓰느라 독자가 원인이나 실행 순서를 복원해야 한다면 설명을 늘린다. 사용자가 자세한 설명을 요구하면 필요한 분량을 쓴다.
- 문체를 다듬어도 사실, 수치, 인용, 불확실성의 정도를 바꾸지 않는다. 윤문 과정과 등급은 요청받지 않으면 결과에 붙이지 않는다.

예: "본 기능을 통해 데이터에 대한 검증의 수행이 가능해집니다."는 "이 기능은 입력 데이터를 검증한다."로 쓴다.

## 완료 조건

`session_get`에 `full:true`를 지정해 작성한 내용을 전체 재확인한다. 핵심 답이 앞에 있는지, 요청한 범위가 빠지지 않았는지, 도식과 본문이 맞는지, 출처와 불확실성이 정확한지 확인하고 고친다. 화면을 실제로 확인하지 않았다면 시각 검증을 했다고 말하지 않는다.

작성이 끝나면 확보한 lease를 종료한다. 중단되었으면 미완료 상태와 사유를 명시한다. 최종 채팅에는 작성 결과와 도구가 반환한 보드 링크 또는 식별자를 짧게 남긴다. 링크를 추측해서 만들거나 본문을 채팅에 다시 복제하지 않는다.
